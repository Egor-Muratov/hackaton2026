# ML: договорённости (дни 1–2)

Автор: ML-специалист. Репетиция на Kaggle Store Sales (Favorita): 54 магазина × 33 семейства = 1782 ряда, горизонт 16 дней, RMSLE. Данных пока нет, оценки ниже взяты из знания соревнования и на репетиции их нужно перепроверить.

## 1. Первые 30 минут с данными

- [ ] **Формат и ключи.** Длинная таблица `date, store_nbr, family, sales, onpromotion`. Проверить, что пары (ключ, дата) уникальны, и выписать диапазоны дат: train до 2017-08-15, test с 2017-08-16 по 2017-08-31.
- [ ] **Дыры в датах.** В train нет 25 декабря, 1 января почти всё закрыто. Достроить полную сетку дат по каждому ряду и пропуски заполнить нулями. Отдельно пометить дни, когда магазин закрыт.
- [ ] **Нули.** Найти ряды, где продажи всегда 0 (например, BOOKS в части магазинов), и магазины, открытые позже начала train (до открытия у них длинные нули). Ряд, у которого 0 за последние ~4 недели, прогнозируем нулём и в модель не отдаём.
- [ ] **Утечки.** Колонка `transactions` в test отсутствует, поэтому её можно брать только с лагом не меньше 16 дней. `onpromotion` в test есть, то есть это известный будущий признак, его использовать можно. Лаги `sales` должны быть ≥16 дней, иначе нужна рекурсивная или direct-схема. Все скользящие окна сдвигаем на горизонт.
- [ ] **Аномалии.** Землетрясение 2016-04-16 вызвало всплеск примерно на 2–4 недели. Эти даты ставим под флаг или выбрасываем из обучения. Начало 2013 года шумное, и обучения с 2015–2016 годов обычно хватает.
- [ ] **Зарплатные дни.** В госсекторе зарплату платят 15-го и в последний день месяца. Нужны признаки `is_payday` и `days_since_payday`.
- [ ] **Праздники.** В `holidays_events` есть поля `type` (Holiday/Transfer/Additional/Bridge/Work Day/Event), `locale` (National/Regional/Local) и `transferred`. Если `transferred=True`, праздника фактически не было, он перенесён на строку с типом Transfer. Региональные и местные праздники сопоставляются со `stores.state` и `stores.city`. Строка Work Day означает рабочую субботу.
- [ ] **Нефть.** В `oil` пропущены выходные и есть NaN, их заполняем ffill или интерполяцией. На прогноз нефть влияет слабо, это макро-тренд.
- [ ] **Быстрые графики.** Суммарные продажи по дням, профиль по дням недели, доля промо по семействам, 5 случайных рядов.

## 2. Где план расходится с задачей и как сделать пайплайн универсальным

| В плане | В Store Sales | Решение |
| --- | --- | --- |
| Метрики MAE, RMSE, MAPE/SMAPE | RMSLE | Метрика задаётся в конфиге. При RMSLE обучаем на `log1p(y)` с L2-лоссом (это напрямую оптимизирует метрику), прогноз переводим через `expm1` и обрезаем снизу нулём. MAPE на нулях не работает, поэтому её не используем. |
| Праздники РФ | Эквадор, причём праздники национальные, региональные и местные, а также переносы | Страна в конфиге берётся из библиотеки `holidays`. Если у организаторов есть свой файл праздников, он важнее библиотеки, а региональные праздники джойним по атрибутам ряда. |
| Один ряд | 1782 ряда | Одна глобальная модель на все ряды. Ключи рядов передаются списком колонок, категориальные признаки ряда (магазин, семейство, тип и кластер магазина) идут в модель. |
| Экзогенных регрессоров нет | Нефть, промо, транзакции | В конфиге два списка: «известны в будущем» (промо, праздники) и «известны только в прошлом» (нефть, транзакции, используются с лагом ≥ горизонта). |

Пример конфига (`ml/config.yaml`):
```yaml
target: sales
date_col: date
series_keys: [store_nbr, family]
freq: D
horizon: 16
metric: rmsle            # mae | rmse | rmsle | smape
target_transform: log1p  # none | log1p
holidays: {country: EC, file: holidays_events.csv, regional_match: {Regional: state, Local: city}}
exog_future: [onpromotion]
exog_past: [dcoilwtico, transactions]
static: [store_type, cluster, city]
lags: [16, 21, 28, 35, 364]
windows: [7, 14, 28, 56]
cv: {folds: 4, step_days: 16}
```

## 3. Лестница моделей и валидация

Валидация: holdout на последних 16 днях train (2017-07-31 – 2017-08-15) плюс 3–4 скользящих фолда, каждый сдвинут назад на 16 дней (expanding window). Признаки на каждом фолде пересчитываются только по данным до отсечки. Фолды должны покрывать разные дни месяца, чтобы в них попали зарплатные дни.

| Шаг | Модель | Ожидаемый RMSLE на валидации (порядок) | Время |
| --- | --- | --- | --- |
| 0 | Все нули (проверка, что метрика считается) | ~3+ | 5 мин |
| 1 | Naive: последнее значение | ~0.55–0.65 | 10 мин |
| 2 | Сезонный naive: значение неделю назад | ~0.50–0.60 | 10 мин |
| 3 | Среднее по дню недели за 2–4 недели, считается в log-пространстве | ~0.45–0.50 | 20 мин |
| 4 | LightGBM на всех рядах: лаги, окна, календарь, праздники, промо | ~0.38–0.42 | 2–3 ч |

Ориентир: топ публичного лидерборда около 0.38. До конца первого дня в прод уходит шаг 3, на второй день его заменяет LightGBM. Если LightGBM не обгоняет шаг 3 на 0.03 и больше, ищем утечку или ошибку в лагах.

## 4. Черновик контракта C# API ↔ ML-сервис (со стороны ML)

История не передаётся в теле запроса: по Store Sales это около 3 млн строк. C# кладёт датасет в общее хранилище (БД или volume) и передаёт ссылку. Обучение запускается асинхронно.

`POST /train` с телом `{ "dataset_ref": "store-sales/v1", "config_overrides": {} }` возвращает `{ "job_id", "status" }`. Статус проверяется через `GET /train/{job_id}`, результат содержит `model_version` и `cv_metrics`.

`POST /predict`, запрос:
```json
{
  "model_version": "latest",
  "dataset_ref": "store-sales/v1",
  "cutoff_date": "2017-08-15",
  "horizon": 16,
  "series": [{"store_nbr": 1, "family": "BEVERAGES"}],
  "history": null,
  "exog_future": [{"date": "2017-08-16", "store_nbr": 1, "family": "BEVERAGES", "onpromotion": 3}],
  "quantiles": [0.1, 0.9]
}
```
Поле `series` можно не передавать или передать пустым, тогда прогноз строится по всем рядам. Поле `history` опционально: это inline-история в том же длинном формате, для демо на одном ряду и для фронта. Ключи рядов имеют тип `object`, их имена берутся из `series_keys` конфига, поэтому C# не зависит от конкретной задачи.

Ответ (длинный формат: 1782 × 16 ≈ 28,5 тыс. строк, это нормально):
```json
{
  "model_version": "lgbm-2017-08-15-a1b2",
  "metric": {"name": "rmsle", "cv": 0.401, "baseline_cv": 0.47},
  "predictions": [
    {"store_nbr": 1, "family": "BEVERAGES", "date": "2017-08-16",
     "yhat": 2315.4, "lower": 1840.0, "upper": 2890.2}
  ],
  "warnings": ["series_all_zero: 52"]
}
```
`GET /health` возвращает `{status, model_version, loaded_at}`.

**Интервалы. Рекомендация:** использовать эмпирические квантили остатков с CV-фолдов, считать их в `log1p`-пространстве отдельно для каждого шага горизонта (1..16) и каждой группы (семейство), а затем переводить через `expm1` и обрезать нулём. Так получается одна модель вместо трёх, интервал честно расширяется с горизонтом и считается за минуты (по сути это split-conformal). Квантильный LightGBM (`objective=quantile`, α=0.1/0.9) оставляем на второй день как опцию: он втрое дороже в обучении, а квантили у него могут пересекаться. Интервал по умолчанию 80%, его уровень задаётся в `quantiles`.

**Согласовать с C#:** snake_case в JSON; даты в ISO без времени; `yhat`, `lower` и `upper` имеют тип double и не могут быть отрицательными; `null` вместо NaN; тайм-аут `/predict` не меньше 30 с, а `/train` только асинхронный; где лежит `dataset_ref` (Postgres или общий volume); коды ошибок 422 (валидация) и 503 (модель не загружена).
