# Фронтенд: стек, экраны, контракт, страховка демо

Дни 1–2 · роль: Фронтенд · репетиция: Kaggle Store Sales (54 магазина × 33 семейства = 1782 ряда, ~1600 дней истории, горизонт 16 дней)

## 1. Стек (решение)

| Что | Решение | Почему |
| --- | --- | --- |
| Сборка | **Vite + React + TypeScript** (Node 24 / npm 11) | `npm create vite@latest -- --template react-ts`, старт за минуту, dev-прокси `/api` на C# API без CORS. |
| Графики | **ECharts** (`echarts` + `echarts-for-react`) | Зум из коробки (`dataZoom`: колесо + слайдер), canvas спокойно тянет 1600+ точек и несколько серий. Интервал рисуется полосой через стек двух area (`lo` + `hi−lo`). В Recharts зума нет (только Brush), а SVG на 1600 точек с тултипами заметно тормозит. |
| UI-кит | **Ant Design** | Бесплатно даёт всё для дашборда: Table с сортировкой, фильтрами и серверной пагинацией, Select с поиском, Upload, Segmented, Statistic. В MUI для этого нужен DataGrid, а у бесплатной версии ограничения (размер страницы до 100). |
| Клиент API | **orval** | Из `openapi.json` генерирует типы и готовые хуки React Query, а также MSW-моки для разработки, пока нет бэка. Перегенерация одной командой: `npm run api`. |
| Данные | **TanStack React Query** | Кэш по ключу (магазин, семейство, горизонт), loading/error-состояния и повтор запросов без лишнего кода. Для загрузки файла: `useMutation` + опрос статуса через `refetchInterval`. |

Версии фиксируем на 7-й день (`package-lock.json` в репо, `npm ci`). Состояние фильтров храним в URL (`?store=all&family=GROCERY I&h=16`): так ссылку на нужный вид можно отправить в чат или открыть на защите.

## 2. Экраны и компоненты

Один экран-дашборд и отдельная вкладка «Данные».

**Первые 3 часа (сквозной сценарий):**
- `FilterBar`: магазин (Select с поиском, по умолчанию «Все»), семейство («Все»), горизонт (Segmented 7/14/16).
- `ForecastChart`: линия факта, линия прогноза пунктиром, интервал полосой, вертикальная линия «сегодня», `dataZoom` с начальным окном ~90 дней до конца истории.
- `MetricsCards`: RMSLE (метрика Kaggle), MAE, MAPE и прирост к бейзлайну.
- `ForecastTable`: таблица прогноза на горизонт (дата, прогноз, нижняя и верхняя граница).
- `ExportCsvButton`: CSV собираем на клиенте из уже загруженного прогноза, отдельный эндпоинт не нужен.
- Состояния загрузки, пустых данных и ошибки, плашка «ДЕМО-ДАННЫЕ» в мок-режиме.

**Потом (после рабочего сквозного сценария):**
- Вкладка «Данные»: Upload CSV, статус задачи, отчёт валидации (строки, ошибки).
- `SeriesTable`: список рядов с серверной пагинацией и сортировкой по объёму продаж или ошибке; клик открывает ряд на графике.
- Маркеры праздников и промо на графике, переключатель «линейная / лог-шкала».
- Сравнение с бейзлайном второй линией, тёмная тема, полировка под слайды.

## 3. Что фронту нужно от API (вход для C#-бэкенда)

Общие правила: JSON в camelCase, даты строкой `YYYY-MM-DD` без времени и часового пояса, пропуски передаём как `null` (не 0), ошибки в формате ProblemDetails, всё под префиксом `/api`. OpenAPI-спецификация доступна по `/swagger/v1/swagger.json`.

1. `GET /api/meta` возвращает `stores[] {storeNbr, city, state, type, cluster}`, `families[]`, `historyFrom`, `historyTo`, `maxHorizon` (16), `intervalLevel` (например 0.8), `modelVersion`.
2. `GET /api/series?store=&family=&sort=sales|error&page=1&pageSize=50` возвращает `{items[], total, page, pageSize}`. Поля элемента: `storeNbr`, `family`, `totalSales`, `lastDate`, `rmsle`. Пагинация серверная: 1782 ряда целиком таблице не нужны.
3. `GET /api/forecast?store={n|all}&family={name|all}&horizon=16&historyDays=` возвращает:
   - `history[] {date, sales, onpromotion}`;
   - `forecast[] {date, yhat, lo, hi}`;
   - `metrics {rmsle, mae, mape, baselineRmsle}`, `intervalLevel`, `modelVersion`, `generatedAt`.
   
   По умолчанию отдаём всю историю ряда (~1600 точек, это ~50 КБ, нормально). Параметр `historyDays` нужен для агрегатов и быстрых ответов.
4. **Агрегаты** (`store=all` и/или `family=all`) считает бэкенд. Интервалы агрегата должны прийти от ML: границы рядов складывать нельзя, сумма квантилей не равна квантилю суммы. Если ML не успевает, бэк отдаёт `lo/hi = null`, и фронт просто не рисует полосу.
5. `POST /api/uploads` (multipart) возвращает `{jobId}`. `GET /api/jobs/{id}` возвращает `{status: queued|running|done|failed, rows, errors[] {line, message}}`.
6. `GET /api/health` для индикатора в шапке и автоматического переключения в мок-режим.

## 4. Страховка демо

- **Мок-режим.** Включается флагом `VITE_API_MODE=mock` или автоматически, если `/api/health` не ответил за 3 с; в шапке тогда видна плашка. Источник данных: статические JSON в `public/mock/` (`meta.json`, `series.json`, `forecast_all_all.json` и 2–3 «красивых» ряда, например `forecast_44_GROCERY I.json`). Их генерируем реальными ответами API (`curl` в скрипт `make mock`) сразу после первого успешного сквозного прогона, а затем обновляем после каждой новой модели. Переключение сделано в одном месте, в mutator у orval, поэтому компоненты о режиме не знают.
- **Офлайн-сборка.** `npm run build` с мок-режимом даёт папку `dist/`, которая открывается через `npx vite preview` на ноутбуке без сети и без бэка.
- **Видео.** После код-фриза записываем 60–90 с через OBS по демо-сценарию капитана: агрегат → зум → конкретный магазин/семейство → таблица → экспорт CSV → метрики. Две копии: на ноутбуке и в общем канале. На репетиции (дни 5–6) записываем пробное видео и засекаем время.
- **Порядок на защите:** прод → локальный мок-режим → видео. Переход к следующему варианту, если что-то не отвечает дольше 10 секунд.
