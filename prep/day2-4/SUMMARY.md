## Что нашла репетиция (главное)

1. **Сеть — главный пожиратель времени.**
   - Прокси даёт 20–40 КБ/с и рвёт соединения.
   - Демону Docker Hub недоступен напрямую.
   - Сколько ушло на загрузки: NuGet (51 МБ) — 10 мин; Python-колёса для заглушки (31 МБ) — 35 мин; npm — больше часа, и фронт так и не собрался. pandas и lightgbm к концу этапа ещё не скачались.
   - **Вывод:** офлайн-запас (wheels, NuGet, npm, `docker save` базовых образов) делается заранее и приносится с собой. Это задача номер один на дни 5–6.
2. **Корпоративные конфиги ломают «голую» машину.** Глобальный `NuGet.config` указывал на недоступный фид. Решение: в шаблоне свой `nuget.config` с `<clear/>`. Для pip и npm проверять так же.
3. **Версии, закреплённые вслепую, не совпадают со скачанными** (fastapi 0.115 против 0.143, numpy 2.1 против 2.4). Правило: версии закрепляются по содержимому `offline/`.
3a. **Без lock-файла офлайн-установка не воспроизводится.** `npm install --offline` резолвит свежие версии (antd 5.29.3), а в кэше лежат другие. В шаблон коммитим `package-lock.json`, офлайн-запас собираем по нему (`npm ci`).
3b. **В фоновых скриптах загрузки — `set -o pipefail`.** Прогрев npm упал через 63 мин с `EIDLETIMEOUT`, но `| tail` вернул код 0, и сбой выглядел как успех.
4. **Тяжёлые инструменты не берём.** Из-за orval установка npm растянулась больше чем на час. Клиент API написан руками по контракту за минуты.
5. **FK в схеме замедлял импорт в 5 раз** (106 с → 22 с). На время COPY ключ снимаем.
6. Мой собственный ложный вывод: «Docker Hub доступен», потому что `hello-world` уже лежал локально. Доступ проверяем через `check-network.sh` (доступность **и** скорость), а не одной командой.

## Фиксация базовых образов (2026-10-12)

Плавающие теги (`sdk:10.0`, `python:3.11-slim`, `nginx:alpine`) запрещены. Под ними в любой момент может выйти новая версия.

- `infra/images.txt` — точные теги, выбираются вручную. `make pin-images` получает digest-ы → `infra/images.lock` → переписывает все ссылки.
- `infra/images.lock` — единственный источник правды: `ARG` в Dockerfile (`FROM ${VAR}`), значения по умолчанию в compose, переменные CI, `offline-pack`.
- `make check-images` (и CI-джоб `images-pinned`) падает при расхождении с lock или плавающем `FROM`.

| Образ | Тег |
| --- | --- |
| postgres | `16.15-alpine3.24` |
| nginx (шлюз и статика фронта, раньше были разные) | `1.30.5-alpine3.24` |
| python | `3.11.17-slim-bookworm` |
| node | `24.21.0-alpine3.24` |
| dotnet sdk / aspnet | `10.0.401` / `10.0.12` (SDK 10.0.111 с машины есть только в дистрибутиве, в MCR его нет) |
| CI: docker cli/dind, alpine | `29.9.0`, `3.24.2` |

**Ловушка, найденная проверкой.** В классическом хранилище Docker (overlay2) после `docker save` → `docker load` у образа пропадает digest (`RepoDigests=[]`), а без явного тега и само имя. `FROM тег@digest` на VM без сети не находит образ и идёт в интернет. Запас выглядел бы готовым, но не работал бы.

Решение: офлайн-ссылки идут без digest, а неизменность проверяется по ID.
- `offline-pack` сохраняет образ по точному тегу без digest и записывает ID образа в файл `.id`.
- `offline-load` загружает образы и сверяет ID с записанным.
- `OFFLINE=1` → `images-env.sh` передаёт в compose и Dockerfile ссылки без digest.

**Проверено.** Удалил 6 образов → `offline-load` (44 с, все ID совпали) → `docker compose build ml` с `OFFLINE=1` и `BUILD_NETWORK=none` → собрано за 39 с. После сборки у `python` по-прежнему `RepoDigests=[]`, то есть registry не использовался.
